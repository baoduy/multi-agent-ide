## R-01: node-pty Integration in Electron Daemon

**Question**: How does node-pty integrate in the Electron/Node.js daemon process?

**Decision**: Use `node-pty` in `packages/daemon` (the daemon is a forked child process that runs in Node.js context under Electron's embedded Node runtime).

**Rationale**:
- node-pty is a native Node.js addon. The daemon is spawned via `child_process.fork()` from the Electron main process, so it shares Electron's Node.js ABI version.
- node-pty must therefore be rebuilt for Electron's specific Node.js ABI using `@electron/rebuild` (or `electron-rebuild`). This is a standard requirement in the Electron ecosystem.
- node-pty spawns a real PTY (pseudoterminal) — giving full shell support: prompts, cursor control, tab completion, SIGWINCH resizing. This is what separates it from plain `child_process.spawn()`.
- The daemon already uses `child_process.spawn()` for the onboard/upgrade flows. For interactive terminal sessions, only node-pty provides the PTY discipline needed.

**Alternatives considered**:
- `child_process.spawn()` with shell=true — already used for onboard/upgrade readonly output. Lacks PTY discipline; programs that check `isatty()` behave differently (no color, no interactive prompts).
- External terminal emulator launch — out of scope; goal is in-app terminal.

**Build requirement**: Add `@electron/rebuild` to devDependencies at root. Add a `postinstall` script: `electron-rebuild -f -w node-pty`. Add `asarUnpack` to `electron-builder.yml` so the native `.node` binary is unpacked from the asar archive at runtime.

## R-02: ANSI Escape Code Handling

**Question**: When node-pty streams raw PTY output (which contains VT100/ANSI escape sequences), how should it be handled?

**Decision**: Strip ANSI escape codes in the daemon (`TerminalApplicationService`) before emitting IPC events, using `strip-ansi@6.0.1` (CommonJS-compatible version).

**Rationale**:
- The UI renders terminal output in a `<pre>` element. Embedding raw ANSI sequences in DOM text produces garbled display (`\x1b[32m` characters appear as literal text).
- Stripping in the daemon keeps the IPC payload clean (plain text), avoids the renderer having to import a stripping library, and reduces payload size.
- `strip-ansi@6.0.1` is used (not v7+) because the daemon targets CommonJS module format. v7 is ESM-only.
- This is an MVP tradeoff: no cursor movement, no color differentiation. If richer rendering is needed later, xterm.js can be added as a rendering layer and raw output passed through instead.

**Alternatives considered**:
- Pass raw output to UI and strip there — burdens renderer, leaks escape codes into the IPC contract.
- `xterm.js` renderer in UI — full VT100 emulation, correct colors and cursor. Adds ~600KB to the bundle and increases implementation scope significantly. Deferred to a future enhancement.

## R-03: Readonly vs Interactive Mode Boundary

**Question**: What is the exact behavioral boundary between readonly and full interactive mode? Can a single component instance switch modes?

**Decision**: `MagentaTerminal` is a stateless-rendering component that is mode-locked by the `readonly` prop. Mode is set at render time by the parent and not toggled dynamically.

**Rationale**:
- Readonly mode consumes an `output` string prop and renders it. No PTY session, no IPC subscriptions beyond what the parent (onboardStore) already manages.
- Interactive mode manages its own PTY session lifecycle via `terminalStore`. It opens a session on mount and closes it on unmount.
- Because readonly is fully controlled by its parent (the dialog), and interactive is self-managed (the sidebar), switching modes mid-lifetime would introduce complex teardown/re-establishment logic with no real use case.
- The spec does not require runtime mode-switching; readonly is for dialogs (controlled by parent store), interactive is for the sidebar (persistent session).

## R-04: IPC Session Identity and Lifecycle

**Question**: How are PTY sessions identified, created, and destroyed across the IPC boundary?

**Decision**: Each PTY session is assigned a `sessionId` (ULID) generated by the daemon at spawn time. The UI stores this and uses it for all subsequent `terminal:input`, `terminal:resize`, and `terminal:close` requests.

**Rationale**:
- ULID is already used in the codebase (`ulid` package is a dependency). Using it for session identity is consistent.
- The daemon's `TerminalApplicationService` maintains a `Map<sessionId, IPty>`. This is the same pattern used by `OnboardApplicationService` with `Map<repoPath, ChildProcess>` for onboard/upgrade process tracking.
- Session cleanup: the service closes the PTY and removes from the map on `terminal:close` request or when the PTY process exits naturally. The UI receives a `terminal:exited` event either way.

## R-05: ActivityPanel Terminal Placement

**Question**: Where exactly does the full interactive terminal go in the ActivityPanel?

**Decision**: Add a new collapsible `Section` titled "Terminal" immediately after the Legend section at the bottom of `ActivityPanel`. The section renders `<MagentaTerminal readonly={false} />` with a fixed max-height to avoid collapsing the Files section.

**Rationale**:
- The `ActivityPanel` structure currently has: Files section (flex: 1, scrollable) → Legend section (fixed, flexShrink: 0).
- The terminal section must not push the Files section out. Implementation: give the terminal section a fixed `height` or `maxHeight` of ~200px, `flexShrink: 0`. The Files section keeps `flex: 1` and scrolls internally.
- `cwd` for the sidebar terminal defaults to `activeRepoPath` from `repoStore`, or `process.cwd()` if no repo is selected. This makes the sidebar terminal immediately useful in repo context.

## R-06: electron-builder asarUnpack for Native Modules

**Question**: Does `electron-builder` need special configuration for node-pty's native binary?

**Decision**: Add `asarUnpack` entry to `electron-builder.yml`:
```yaml
asarUnpack:
  - "**/node_modules/node-pty/**"
```

**Rationale**:
- Native `.node` addon files cannot be `require()`d from inside an asar archive — Node.js's native module loader requires a real filesystem path.
- `asarUnpack` tells electron-builder to extract matching paths from the asar, placing them in `app.asar.unpacked/` alongside the archive. Node.js resolves them correctly at runtime.
- This is the standard documented approach for native modules in electron-builder projects.
